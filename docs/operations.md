# Local operations

Run commands from the repository root. See the [README](../README.md) for first
installation and the [configuration guide](../config/README.md) for AWS values.

## Choose the startup mode

| Mode | Data source | AWS access | New EMR job |
| --- | --- | --- | --- |
| `python app.py --demo` | Bundled synthetic fixture | None | No |
| `python app.py --offline` | `runtime/results.json` | None | No |
| `python app.py --profile your-profile` | Previously completed S3 output | S3 reads | No |
| `python app.py --profile your-profile --run-job` | New Spark analysis | S3 and EMR | Yes, billable |

Use `.\.venv\Scripts\python.exe` in place of `python` on Windows to select the
project environment. Replace `your-profile` with your existing AWS CLI profile
name. The completed analysis run already supplies the real results;
normal demonstrations use `--offline`. The browser has no job-submission action.

## Health and troubleshooting

The Python app serves <http://localhost:8000/>. Docker Compose serves
<http://localhost:8002/>. Its health check uses `/api/health`, which reports ready
state and result provenance; it does not poll AWS on each request. Confirm the
mode, offline flag and job ID when distinguishing real saved output from demo data.

```powershell
docker compose ps
docker compose logs --tail 50 web
Invoke-RestMethod http://localhost:8002/api/health
Invoke-RestMethod http://localhost:8002/api/users/214328887
```

For the recorded cloud run, user 214328887 has 180 followers and 214 followees;
user 107830991 has 180 followers and 157 followees. See [cloud evidence](qa/TEST-RESULTS.md).

| Symptom | Action |
| --- | --- |
| Offline startup says no local results | Restore your private cache to `runtime/results.json`, or load the existing S3 result using the profile command above |
| Missing `config/local.json` | Follow the configuration guide; offline/demo modes do not need it |
| Expired AWS login while reading S3 | Sign in again with `aws login --profile your-profile --region ap-southeast-2`, then reload saved results |
| Homepage reports missing frontend build | Run `npm.cmd --prefix frontend run build`, or use the Vite development server |
| Port is occupied | Stop the older instance, or start Python with `--port 8001` |
| Container fails to start | Inspect its logs and confirm `runtime/results.json` exists on the host |

The app logs startup, result metrics and any explicitly requested EMR job states
to its terminal. The container sends these logs to Docker. No central monitoring,
automatic cloud deployment or always-running job scheduler is configured.

## Saved results and shutdown

`runtime/results.json` is generated by loading completed S3 output and is reused
for offline startup. The directory used to be named `work/`; it has been moved,
with the saved result contents preserved. Keep a private backup for later
demonstrations. Deleting this cache disables real offline mode until restored or
reloaded from S3. It does not delete the completed cloud output.

Compose mounts `runtime/` read-only. Stop it with `docker compose down`; this
preserves the host cache. Stop a terminal app with Ctrl+C. Searches and ordinary
web startup do not submit another EMR job.

An EMR job is a usage charge for that execution, not a scheduled monthly job.
Retained S3 objects/logs can continue to incur storage charges. Preserve local
results and report evidence before deliberately removing AWS resources. This
repository cleanup does not delete resources or submit any new analysis.

## Infrastructure, DevOps and SRE

- **Infrastructure** is the set of cloud resources. `infra/` defines the S3,
  IAM and EMR resources in Terraform.
- **DevOps** covers how development and operations deliver changes together.
  Here, GitHub workflows check builds/tests and optionally publish a container;
  the Docker files define its packaging and local execution.
- **SRE** applies engineering to service reliability: service objectives,
  monitoring, incident response, recovery and safe changes. This prototype has
  health checks, failure handling and this operations guide, but no formal SLO,
  on-call process or production reliability claim.

These responsibilities overlap. They do not require three parallel source
folders. Public Fargate/EC2 hosting would need a separate access, monitoring and
recovery design; see the [architecture](architecture/ARCHITECTURE.md).
